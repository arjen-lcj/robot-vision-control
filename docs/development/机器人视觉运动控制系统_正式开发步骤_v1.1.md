## 0. 文档目的与执行规则

本文规定从空工程目录到可演示机器人原型的开发顺序。每个阶段都定义要做什么、留下什么资料、如何验收，以及验收失败时的处理方式。本文不提供驱动源代码、固件代码或上位机代码。

### 0.1 开发原则

1. **能自研的项目代码尽量自研。** AP3216C、ICM20608、IMX415 传感器侧驱动、设备树配置、Linux 用户态服务、CAN 协议、F407 电机固件、电脑上位机都纳入自己的实现范围。
2. **复用必要的 Linux 底层。** 复用内核驱动框架、SoC 的时钟/复位/pinctrl/GPIO/I²C/SPI 控制器、存储、以太网、显示、RK3588 的 CSI/ISP 等平台支撑。重写这些底层会把项目变成 SoC 移植工作，不能有效增加本项目的驱动学习价值。
3. **厂商原始资料只作基线和对照。** 原厂 SDK、镜像、设备树和驱动源码保存为未修改的参考副本；自己写的模块、设备树、补丁和构建说明放在项目自己的目录或 Git 分支。不要把供应商原文件直接改成唯一版本。
4. **同一设备同时只能由一个驱动负责。** 自研驱动接管传感器前，需先确认厂商驱动已卸载、解绑或在自己的设备树配置中禁用。禁止两份驱动同时争用同一 I²C/SPI 设备。
5. **硬件先验收，再进入下一阶段。** 当前阶段未通过，不要通过“同时多改几项”掩盖问题。先判断是供电、连线、设备树、驱动、协议还是用户态问题。
6. **安全优先于完整功能。** 电机上电和机械运动要按本文的低风险顺序进行。软件急停不能代替实体断电/驱动禁能。
7. **把事实和方案分开记录。** 板卡丝印、原理图、内核版本、传感器读数属于事实；CAN 波特率、速度限制、超时时间等在实测冻结前属于方案值。

### 0.2 阶段门禁

- 每一阶段结束时，按“验收清单”逐项记录通过/未通过，并附日志、照片、版本信息或曲线。
- 未通过项记录在问题清单中，包含复现步骤、预期、实际结果和下一步排查方向。
- 没有可恢复的系统镜像或启动方式时，不进行内核、设备树和启动链修改。
- 任何“偶尔能工作”“重启后不知道能否恢复”的功能都不能标记为通过。

## 1. 最终交付目标

完成一个差速移动机器人原型，具备以下能力：

1. RK3588 使用 MCIMX415 获取视频，在本地屏幕和电脑上位机显示；完成摄像头链路分析，并尝试自研 IMX415 传感器侧 V4L2 驱动。
2. RK3588 与电脑通过以太网交换视频、控制命令和状态信息。
3. STM32F407 读取左右电机编码器、运行本地速度闭环、输出 PWM 和方向信号，并通过 CAN 收发命令/反馈。
4. i.MX6ULL 上自己实现 AP3216C I²C 驱动和 ICM20608 SPI 驱动，按合适的 Linux 子系统向用户态提供数据；同时监听和记录 CAN。
5. RK3588、i.MX6ULL、F407 各自的屏幕显示本地有用状态；电脑上位机提供系统总览。
6. 命令超时、网络断开、CAN 故障和实体急停都有预期且实测的安全行为。
7. 工程包含硬件清单、连接说明、设备树/驱动构建步骤、协议文档、验收记录和演示材料。

STM32F103 不进入第一版关键路径。完成核心系统后，再把它作为辅助 I/O 或协议测试节点加入。

## 3. 阶段一：硬件盘点与实物接口确认

### 目标

确认手头实物、官方资料和项目假设一致，避免因板卡版本、屏幕型号或接口电平不同造成后续返工。

### 操作步骤

1. 给每块板拍摄正面、背面和接口近照；记录板卡型号、底板版本丝印、核心板型号和屏幕型号。
2. 给 IMX415 模组拍照，记录模组版本、排线长度、连接器方向和镜头方向；检查开发板 CSI 插座丝印。
3. 对照原理图确认 i.MX6ULL 的 I²C/SPI 外设连接、F407 的 CAN 收发器/端接跳线、RK3588 的 CAN 收发器/端接以及各板扩展接口的逻辑电压。
4. 检查三块屏的接口、分辨率、触摸控制器和实际连接线；记录触摸是否可用，不把“有屏幕”默认等同于“支持触摸”。
5. 先填硬件清单和接口矩阵。接口矩阵至少包含：信号名、发送节点、接收节点、连接器/引脚、逻辑电平、供电、接口协议、共享/复用情况、验证状态。
6. 盘点 CAN 总线的收发器、终端电阻跳线和可用线材。确认终端电阻只在总线物理两端启用。
7. 电机与驱动器尚未确定时只记录选型要求，不做电机上电实验。选型必须包含额定电压、堵转电流、编码器输出方式和驱动器持续/峰值电流。

### 必须输出

- hardware/bom/inventory.md：已有设备和计划购买设备清单。
- hardware/wiring/interface_matrix.md：逐信号接口矩阵。
- docs/hardware/photos/：板卡照片，文件名包含板卡和版本。
- docs/boards/version_matrix.md：硬件版本与软件版本对应表。
- docs/architecture/system-overview.md：标注已确认链路和待确认链路。

### 验收条件

- [ ] 每块板和每块屏都能通过型号/丝印区分。
- [ ] IMX415 排线方向、使用的 CSI 插座和供电要求已查明。
- [ ] CAN 三个节点的物理收发路径已确认；逻辑 TX/RX 未被误当作 CANH/CANL。
- [ ] I²C、SPI、CAN、电机电源和逻辑电源的接口矩阵没有未知电压。
- [ ] 未确认的引脚/跳线在文档中明确标为“待确认”，没有用猜测值替代。

**门禁：** 若 CAN 收发器、屏幕接口电平或摄像头排线方向未知，不进入对应设备的带电连接阶段。

## 4. 阶段二：软件环境与可恢复基线

### 目标

让每块板都能恢复到已知可启动状态，记录自研模块需要匹配的内核、工具链和启动配置。

### 操作步骤

1. 在 version_matrix.md 记录每块 Linux 板的内核版本、设备树型号、根文件系统、启动介质、SDK 版本、交叉编译器和烧录工具；记录 STM32 IDE/编译工具版本和 PC 操作系统。
2. 使用串口控制台连接 RK3588 和 i.MX6ULL，保存一次正常启动日志。确认能进入系统、查看设备信息并正常关机/重启。
3. 备份原厂系统镜像、启动分区或官方烧录包到 system-images；保存校验值、下载来源和备份日期。确认烧录工具能识别设备，但在此阶段不实际覆盖系统。
4. 将厂商 SDK 源码放进 vendor-baseline 的只读目录。记录它对应的硬件版本和镜像，不对该目录执行开发修改。
5. 准备独立 Linux 构建环境。按厂商 SDK 要求安装/选择交叉编译器；RK3588 与 i.MX6ULL 的构建环境分别记录，不共用未经验证的工具链配置。
6. 确认能在当前运行内核版本下编译一个不接管硬件的最小外部模块。该步骤只验证构建链，不开展传感器驱动功能开发。
7. 确认设备树编译和烧录流程；写明恢复旧设备树/镜像的方法。没有可靠恢复路径时不烧录自定义 DTB。

### 版本记录特别要求

正点原子在线资料给出的 i.MX6ULL 阿尔法板 BSP 内核为 4.1.15；实物镜像可能经过更新，所以以设备实际报告的版本为准。RK3588 SDK/摄像头节点配置同样以当前板卡软件包为准。不能只写“Linux”或“厂商系统”，要记到具体版本。[阿尔法板软件资源](https://wiki.alientek.com/docs/Boards/Linux/IMX6U/I.MX6U%20%E5%BF%AB%E9%80%9F%E4%BD%93%E9%AA%8C%E6%89%8B%E5%86%8C/introduction%20to%20software%20and%20hardware%20resources/Introduction%20to%20Software%20Resources/)

### 验收条件

- [ ] 每块板都有独立、可复现的正常启动记录。
- [ ] 原厂镜像/源码备份已保存且有校验值；至少确认一种系统恢复方法。
- [ ] 记录了每块 Linux 板的实际内核和设备树型号。
- [ ] 外部模块构建工具链与目标板内核一致；模块能构建但尚未加载到传感器设备。
- [ ] 自定义设备树编译、保存和回退步骤已写好。

**门禁：** 缺少备份、无法串口恢复或工具链版本不明时，不进入内核模块加载和设备树烧录阶段。

## 5. 阶段三：架构、接口和安全行为冻结

### 目标

在写驱动和固件前确定每条链路由谁负责、数据单位是什么、出现异常时系统如何处理。

### 操作步骤

1. 固定节点职责：RK3588 负责相机、视觉和 PC 通信；F407 负责编码器和电机闭环；i.MX6ULL 负责自己的传感器驱动、CAN 监控和数据记录；PC 是操作台；F103 暂不参与 MVP。
2. 固定视频路径：IMX415 → RK3588 V4L2 → RK 本地显示/推流 → PC RTSP 显示。禁止尝试经 CAN 传输视频。
3. 固定控制路径：PC → 以太网/WebSocket → RK3588 → CAN → F407 → 电机驱动器 → 电机；编码器反馈回 F407，再经 CAN 返回 RK/PC，i.MX6ULL 旁路监听。
4. 明确速度和角速度单位、符号方向、左右轮定义、序号规则、命令有效期、故障码和版本字段。
5. 根据电机编码器与驱动器选型计算轮速、减速比和换算关系；这些参数放进项目配置和协议说明，不散落在界面代码里。
6. 冻结 CAN 帧 ID、字节布局、小端/有符号格式、缩放、频率、心跳和 bus-off 行为。初期按经典 CAN 2.0B 设计；500 kbit/s 是方案起点，需在实物总线上验证。
7. 冻结安全状态：PC 断开、RK 服务停止、CAN 断线、F407 超时、编码器异常和实体急停各自对应什么行为。所有软件故障最终都要由 F407 的本地超时和/或实体急停兜底。
8. 定义本地屏显示内容：RK 相机/识别/链路；F407 轮速/控制/故障；i.MX6ULL 传感器/CAN/日志。

### 必须输出

- docs/architecture/system-overview.md：最终数据流图和节点职责。
- common/protocol/spec/can_protocol.md：CAN 物理层、ID、数据布局和异常行为。
- common/protocol/spec/host_messages.md：WebSocket 消息字段、单位、序号和错误回应。
- tests/acceptance/stage_checklists.md：每个系统需求对应的可验收条件。

### 验收条件

- [ ] 每个数据/命令都有唯一来源和目的节点。
- [ ] 速度单位和坐标方向不会由开发者自行猜测。
- [ ] CAN 物理端接、波特率和 ID 已形成书面约定。
- [ ] 故障时电机安全行为已写明，且不依赖 PC 窗口持续运行。
- [ ] F103 被明确标成 MVP 之外的可选扩展。

**门禁：** 协议、轮速正负方向或超时停车行为未冻结，不开始跨板控制集成。

## 6. 阶段四：每个自研 Linux 驱动的共同流程

所有 AP3216C、ICM20608、IMX415 驱动都按以下流程进行。不要把“模块能加载”当成驱动完成。

### 驱动从零到验收的步骤

1. **设备资料收集：** 读取芯片资料、开发板原理图、模组说明。记录地址/ID、供电、总线、时序、寄存器复位值、中断线、复用脚和可用测量范围。
2. **硬件路径确认：** 确认连接器、SoC 控制器、设备树节点、pinmux、供电和板上电平。标记哪些是硬件事实，哪些是待确认。
3. **厂商基线验证：** 必要时短暂使用原厂系统/例程验证传感器本体和线路。此步骤是硬件对照，不把厂商驱动作为自己的最终实现。
4. **建立自研工作目录：** 在正式仓库的对应设备目录内建立驱动、构建说明、DTS 配置和测试记录；原厂源码目录保持不动。
5. **解决驱动所有权：** 确认设备当前是否已绑定原厂驱动。使用自己的设备树副本/配置禁用原驱动或替换设备匹配项；一次只允许一个驱动控制该设备。
6. **独立构建：** 首先把自研驱动作为外部模块编译，确认目标内核版本、配置和符号一致。不要一次同时改驱动、DTS、用户程序和内核版本。
7. **分层验证：** 先验证 probe/ID，再验证寄存器读写和初始化，再验证一次性测量，再启用连续采样/中断/缓冲。
8. **接入标准子系统：** 传感器使用 IIO；按键接 input；指示灯接 LED；相机传感器接 V4L2 sub-device；CAN 使用 SocketCAN。子系统选型写进 driver-notes。
9. **异常处理：** 验证设备不存在、总线错误、读写失败、重复启动、卸载/重新加载、服务重启和断电重启后的行为。
10. **记录与交付：** 保存驱动版本、DTS 版本、编译日志、启动日志、测量条件、实测数据和已知限制；以一个小而独立的 Git 提交提交。

### 所有驱动的通用验收门槛

- [ ] 设备通过设备树/驱动模型正确枚举，不依赖手工猜设备号。
- [ ] 驱动只拥有自己负责的设备；没有重复绑定和总线争用。
- [ ] 关键错误会被检查并留下可定位的错误信息。
- [ ] 用户态接口遵循合适的内核子系统，而不是为了省事创造私有接口。
- [ ] 能从冷启动重复完成初始化；不靠先运行原厂应用“碰巧配置好硬件”。
- [ ] 文档可以让另一位开发者按同一内核版本重建模块并复现结果。

Linux IIO 用于传感器数据与缓冲采集；设备树描述硬件连接；V4L2 sub-device 用于相机传感器；SocketCAN 用于 Linux CAN 网络接口。实现时分别参考 [IIO 文档](https://docs.kernel.org/driver-api/iio/index.html)、[设备树使用模型](https://docs.kernel.org/devicetree/usage-model.html)、[相机传感器驱动说明](https://docs.kernel.org/6.18/userspace-api/media/drivers/camera-sensor.html) 和 [SocketCAN 文档](https://docs.kernel.org/networking/can.html)。

**目标：** 自己实现 SPI 事务、传感器配置、六轴数据通道和后续缓冲/中断能力。阿尔法板资料说明 ICM20608 接在 ECSPI3，相关管脚与 UART2 复用；改设备树前必须确认调试串口和 SPI pinmux 冲突。[原理图说明](https://wiki.alientek.com/docs/Boards/Linux/IMX6U/I.MX6U%20%E7%A1%AC%E4%BB%B6%E5%8F%82%E8%80%83%E6%89%8B%E5%86%8C/baseboard/)、[传感器测试说明](https://wiki.alientek.com/docs/Boards/Linux/IMX6U/I.MX6U%20%E5%BF%AB%E9%80%9F%E4%BD%93%E9%AA%8C%E6%89%8B%E5%86%8C/function%20test/icm20608_test/)。

#### 步骤

1. 明确 SPI 控制器、片选、模式、最高时钟、复位脚/中断脚和与 UART 的复用冲突。
2. 在原厂系统中确认芯片 ID 和传感器轴向；记录开发板静止时的原始数据，作为连线和轴映射对照。

4. 自己实现复位、量程、采样率、滤波和数据读取；先用轮询实现稳定单次读取，再扩展连续采样。

8. 验证 SPI 失败、设备 ID 错误、持续采样退出、模块卸载和冷启动恢复。

#### 验收

- [ ] 自研驱动能够稳定识别 ICM20608，并在不加载原厂驱动时工作。
- [ ] IIO 能同时读取三轴加速度与三轴角速度；量程、单位和坐标系有书面说明。
- [ ] 固定姿态和翻转测试符合坐标定义；异常数据和总线错误能够定位。
- [ ] 若实现 buffer/IRQ，数据频率和丢样统计已记录；未实现的能力明确标为后续项。

## 8. 阶段六：RK3588 摄像头基线与自研 IMX415 驱动

### 目标

先证明摄像头模组、线缆和 CSI 硬件工作，再自研 IMX415 传感器侧 V4L2 sub-device 驱动。CSI 接收器、ISP、DMA 和内核媒体框架继续使用已存在的 SoC/BSP 驱动。

### 步骤

1. **确认出厂基线：** 记录 SDK、内核、DTB、CSI 插座、视频节点、sensor sub-device、媒体拓扑、当前可用分辨率和帧率。
2. **稳定取流：** 使用原厂软件配置取流并在 RK 本地屏显示；连续运行并保存帧率、丢帧、温度和日志。此阶段不改原厂驱动。

6. **先实现探测：** 先验证供电、时钟、复位和 I²C ID；probe 不成功时只排查这几项，不同时加入 ISP 调参和算法。
7. **实现媒体接口：** 注册 V4L2 sensor sub-device、媒体 pad、格式/分辨率和必要控制；再实现模式配置、流启停、曝光/增益和设备电源管理。
8. **逐级接入链路：** 传感器 ID → sub-device 注册 → media graph 链路 → 单帧/低分辨率采集 → 稳定连续取流 → 本地屏显示 → RTSP 推流 → PC 显示。
9. **确认设备自动发现：** 用户态服务根据配置或媒体拓扑找到正确相机，不写死某个 /dev/video 编号。
10. **如需要 AI：** 先在稳定视频基础上运行轻量模型，再叠加检测框；AI 不作为相机驱动验收的前置条件。

### 验收

- [ ] 原厂基线曾稳定取流，且有可恢复镜像/DTB。
- [ ] 自研驱动在不运行原厂 sensor 驱动时成功读取传感器 ID 并注册 sub-device。
- [ ] 自己的设备树配置与板级接线匹配；媒体拓扑中 sensor、CSI、ISP、video node 关系清楚。
- [ ] 至少一个分辨率模式可以连续取流；流启停和曝光/增益等已实现控制的响应符合预期。
- [ ] 传感器未连接、复位失败、I²C 错误和模式不支持时有明确日志，并可回退原厂配置。
- [ ] 相机节点发现不依赖固定的 /dev/videoX 编号。

**门禁：** 未取得可靠传感器寄存器/时序资料，或原厂图像链路不能稳定工作时，不进入“自研驱动故障定位”阶段；先解决资料或硬件基线问题。

## 9. 阶段七：STM32F407 电机控制固件

### 目标

让 F407 独立完成编码器读取、速度闭环、CAN 通信和超时停车。F407 屏用于本地诊断，不参与实时闭环运算。

3. 不带机械负载验证 PWM、方向、使能和急停输入；用示波器/逻辑分析仪或安全的低压测试方式确认输出，不让车轮意外旋转。
4. 实现 CAN 节点心跳和静态状态帧。用 USB-CAN 或经过确认的测试节点验证 CAN ID、端序、缩放和周期。
5. 实现电机控制任务：CAN 接收与校验、目标缓存、编码器测速、固定周期闭环、PWM 限幅、故障状态和显示刷新分层处理。
6. 加入本地命令有效期；超时、通信错误、编码器异常或实体急停触发时输出安全态。
7. 首次接真实电机时，使用限流电源、保险和实体急停，车轮架空；从单侧低速开始，再逐步进入双轮闭环。
8. 记录目标/实际轮速、控制输出、供电电压、负载和控制周期；调整 PID 时每次只改一组参数并保留前后曲线。
9. 确认 F407 屏幕刷新不会阻塞控制周期；过载或通信中断时状态显示应指出故障。

### 验收

- [ ] 低速单轮和双轮目标能稳定跟随；验收误差阈值根据所选电机冻结并写明测量条件。
- [ ] CAN 命令超时后 F407 在冻结时间内进入安全态。
- [ ] 实体急停能直接禁能/断开电机驱动，不依赖 RK、i.MX6ULL 或 PC。
- [ ] CAN bus-off、编码器断线、目标越界和复位后都不会意外恢复非零速度。

## 10. 阶段八：CAN 三节点联调

### 目标

先证明物理总线和最小协议，再接入完整的三板数据流。Linux 使用 SocketCAN 用户态接口，不另写 CAN 控制器驱动。

### 操作步骤

1. 独立验证每块板 CAN 控制器和收发器；确认供电、共地/隔离方式、CANH/CANL 线序、总线终端和波特率。
2. 用 USB-CAN 连接 F407，先观察心跳和只读状态，再测零速命令；确认 ID、payload、周期和错误计数。
3. 将 F407 接入 RK3588，验证 RK 通过 SocketCAN 收发；先使用不驱动电机的状态模式。
4. 接入 i.MX6ULL，验证它可以同时监听而不影响总线；传感器帧由 i.MX6ULL 发送前先确认频率不会占满总线。
5. 分别拔掉每个节点，记录剩余节点的行为和故障指示；恢复连接后验证节点重新上线。
6. 进行 bus-off/波特率不一致/端接错误等故障演练时，不接电机电源。

### 验收

- [ ] 三节点 CAN ID 无冲突，所有节点波特率一致。
- [ ] 仅总线两端各有一个有效 120 Ω 终端。
- [ ] RK 到 F407 的零速与低速命令可正确识别；F407 状态能到达 RK 和 i.MX6ULL。
- [ ] i.MX6ULL 监听不会改变 F407 控制状态。
- [ ] 节点拔除、恢复、总线错误能记录并显示。
- [ ] 测量 CAN 总线负载和错误统计；本阶段不以猜测的 CAN 帧率作为结论。

## 11. 阶段九：RK3588 服务和电脑上位机

### 11.1 RK3588 服务

**目标：** 管理相机、WebSocket 控制/状态和 CAN 转发。服务不承担 F407 的实时闭环。

#### 步骤

1. 在 software/linux/rk3588/apps 下拆分相机取流、CAN 命令/状态、WebSocket API 和运行配置，不把它们写成一个难以诊断的大进程。
2. 先实现状态端点和只读状态推送，再实现零速/低速命令；任何输入都要检查范围和有效期。
3. 将视频流与控制通道分开；RTSP 用于视频，WebSocket 用于控制/遥测。
4. 断开 PC、停止服务、相机离线和 CAN 离线时显示明确状态；不得让控制命令无限期保持。
5. 将启动服务配置单独保存到 deployment；先手动启动验证，后设置开机自动运行。

#### 验收

- [ ] PC 可连接并收到持续状态；错误格式/超范围命令被拒绝。
- [ ] WebSocket 断连后不会继续发出无限期有效运动目标。
- [ ] 相机 RTSP 与控制/遥测故障可以分开诊断。
- [ ] 服务崩溃后能重启；重启不会向 F407 恢复旧运动命令。

### 11.2 PC 上位机

**目录：** software/host/app/  
**目标：** 自己实现桌面操作台，提供视频、手动控制、节点状态、曲线和日志。

#### 步骤

1. 先建立窗口和页面结构，页面包括主视频、手动控制、节点/传感器状态、曲线、告警和日志。
2. 先接只读状态和日志，不启用运动按钮；检查各字段单位、时间戳和节点离线显示。
3. 增加 RTSP 视频窗口，记录端到端视频延迟和长时间运行表现。
4. 增加键盘/手柄控制前，先实现“失焦归零”“按键松开归零”“连接断开归零”和可见的使能状态。
5. 加入有限速度档位和软件限幅，但将最终命令超时与速度限制放在 RK/F407 端二次检查。
6. 加入曲线、日志导出、运行配置和会话标记；确保故障发生时能回溯时间点。
7. 最后连接真实底盘；先架空车轮，逐级提高速度，检查 UI 线程卡顿不会影响 F407 闭环和超时停车。

#### 验收

- [ ] 视频、控制、遥测分别工作，界面能区分各自掉线。
- [ ] 未连接 RK 或窗口失焦时不能持续产生运动命令。
- [ ] 状态曲线有时间基准，可导出；日志包含命令序号和错误码。
- [ ] 窗口关闭、PC 休眠、网线拔除后，底盘按安全规则停车。

## 12. 阶段十：本地屏幕与端到端集成

### 步骤

1. 先单独验证 RK3588 屏幕能显示相机画面和相机/网络状态；不因上位机已能显示就省略本地诊断。
2. 在 F407 屏幕显示本机目标轮速、反馈轮速、使能、通信和故障状态；确认刷新不阻塞控制循环。
3. 在 i.MX6ULL 屏幕显示 IIO 最近更新时间、CAN 节点心跳、日志容量和服务状态。
4. 建立统一启动顺序：先 F407 零输出启动，再启动 i.MX6ULL 日志节点，再启动 RK3588 相机/服务，最后连接 PC。电机驱动上电放在确认急停和总线在线之后。
5. 进行端到端数据流演示：PC 命令 → RK 速度换算/校验 → CAN → F407 闭环 → 编码器反馈 → PC 曲线；同时 i.MX6ULL 记录 CAN 和传感器数据。
6. 测试三块板各自重启；验证重启节点不会让其他节点卡死或使电机意外恢复运动。

### 验收

- [ ] 三块板的本地屏都显示各自职责相关的状态。
- [ ] 电脑上位机能看到视频、轮速、i.MX6ULL 传感器和节点在线状态。
- [ ] 端到端命令和反馈能使用同一序号/时间窗口关联。
- [ ] 任一 Linux 节点重启或失联时，F407 的本地安全逻辑继续有效。
- [ ] 完成一次可复现的低速运行，不需要临时手工操作隐藏步骤。

## 13. 阶段十一：故障注入、稳定性与安全验收

所有电机故障注入先在车轮架空、限流电源和实体急停就绪的条件下进行。测试过程中设定一名操作者负责急停，不同时更改固件、设备树和接线。

### 故障场景

| 场景 | 操作 | 预期行为 | 记录内容 |
|---|---|---|---|
| PC 网络断开 | 运行中拔掉电脑网线/断开连接 | RK 停止刷新运动目标，F407 超时停车 | 最后命令时间、停车延迟、告警 |
| RK 服务退出 | 停止 RK 控制服务 | F407 超时停车，不保持上次速度 | 服务日志、CAN 最后帧、停车时间 |
| CAN 断开 | 断开总线或关闭某节点 | F407 本地保护；RK/i.MX6ULL 标示节点离线 | 错误计数、bus-off、恢复时间 |
| 传感器断开 | 断开 AP3216C/ICM20608 之一 | 对应驱动/服务报告该传感器故障，其他设备继续工作 | 内核日志、IIO 状态、服务状态 |
| 摄像头断开 | 关闭或断开 IMX415 | 视频窗口报错，控制和电机反馈链仍可诊断 | V4L2/media 日志、服务状态 |
| i.MX6ULL 存储空间不足 | 使用受控测试文件占用空间 | 停止/轮转日志并告警，不影响控制节点 | 剩余空间、日志状态 |
| F407 复位 | 受控复位 MCU | 输出回安全态；重启后等待新使能/有效命令 | 输出波形、心跳和恢复过程 |
| 实体急停 | 低速运行时按下急停 | 电机驱动被直接禁能/断电，软件状态显示急停 | 停机过程、急停回路和复位状态 |

### 稳定性运行

1. 在低速、车轮架空的条件下长时间运行相机、传感器、CAN 记录和 UI。
2. 再在地面低速运行，逐步增加持续时间；每次运行前检查电机/驱动器温度、螺丝、供电和急停。
3. 记录相机帧率/丢帧、控制周期、CAN 错误、传感器采样、日志增长和系统温度。
4. 任何重启、丢帧、掉线或控制异常都归档到问题清单，不用平均值掩盖偶发故障。

### 验收

- [ ] 表中故障场景都有预期行为和实测结论。
- [ ] 网络断开、RK 服务退出或 CAN 丢失不会造成持续运动。
- [ ] 实体急停不依赖操作系统、CAN 或上位机。
- [ ] 连续运行记录中无未解释的重启、驱动崩溃、日志无限增长或重复驱动绑定。
- [ ] 稳定性报告写明测试时长、速度、供电、负载、环境和软件版本。
