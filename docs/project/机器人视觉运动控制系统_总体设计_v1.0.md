# 多节点机器人视觉与运动控制系统总体设计

**版本：** 1.0（总体设计基线）  
**日期：** 2026-10-16  
**目标：** 用现有 RK3588、i.MX6ULL、STM32F407、STM32F103 和电脑，完成一套可演示、可复现、能体现 Linux 驱动与机器人控制能力的移动机器人原型。

> 本文定义项目总体目标、节点职责、数据流、接口方案、风险和验收方向，是跨电脑继续开发时的总体设计基线。逐阶段操作、文件创建和验收步骤见 `docs/development/机器人视觉运动控制系统_正式开发步骤_v1.1.md`。本文不是最终接线图；正式接线前要以手头板卡硬件版本、原理图、接口电压和电机额定参数为准。文中“事实”来自厂商/内核资料；“方案”是本项目建议；“待确认”列出必须实物核对的变量。

## 1. 项目目标

制作一个小型差速移动机器人系统：RK3588 负责摄像头采集、视觉处理和上位机通信；STM32F407 负责电机闭环控制；i.MX6ULL 负责 Linux 传感器驱动、CAN 监控和本地诊断；电脑软件负责操作、视频、状态曲线和日志。STM32F103 作为后续可选的辅助 I/O 或协议测试节点。

这个项目的重点不是把所有板子都堆进系统，而是让每块板承担适合它的工作，并能拿出代码、接口文档、测试记录和演示过程证明工作确实完成。

### 项目边界

- **MVP（第一版必须完成）：** 一路 IMX415 视频；PC 上位机显示视频与状态；F407 通过编码器闭环控制双电机；RK3588 与 F407 交换命令和反馈；i.MX6ULL 上能读取板载传感器并观察/记录 CAN 数据；三个 Linux/MCU 节点和电脑各自的屏幕显示有用状态。
- **增强版：** RK3588 运行轻量目标检测并叠加识别框；i.MX6ULL 将传感器读数通过 IIO 暴露，加入按键中断、日志落盘和启动服务；上位机显示 IMU、接近/光照、轮速、故障和链路状态。
- **可选扩展：** STM32F103 作为辅助 I/O/协议测试节点；加遥控器、超声波或测距传感器。完成 MVP 前不建议为了“功能多”先买这些扩展件。
- **不作为本项目目标：** 安全等级认证、量产级运动安全、复杂导航/建图、功能安全或自动驾驶。演示平台不应被当作可载人或可在公共区域运行的产品。

## 3. 系统结构与数据流

    IMX415 摄像头 ── MIPI CSI / V4L2 ──> RK3588
                                            │
                电脑上位机 <── 以太网 ──────┤
                 RTSP 视频 / WebSocket     │ CAN：目标轮速、状态反馈
                                            ▼
    i.MX6ULL <────────────── CAN ───────> STM32F407 ── PWM/方向 ──> 双路驱动器 ──> 左右电机
       │                                          ▲                         │
       ├─ AP3216C（I²C）                          └──── 编码器反馈 ──────────┘
       └─ ICM20608（SPI）

PC 上位机只向 RK3588 发送控制命令。RK3588 做边界检查和速度换算后，向 F407 发目标轮速；F407 在 MCU 上运行闭环控制。i.MX6ULL 在 MVP 中监听 CAN、采集本机传感器并记录数据，不承担电机实时控制，也不必把视频转发到 CAN。

### 显示器分工

- **RK3588 屏幕：** 本地相机预览、识别框、相机帧率、网络与 CAN 在线状态。
- **F407 屏幕：** 左右目标/实际轮速、控制输出、编码器计数、故障码。控制中断中不刷新屏幕；界面刷新在低优先级任务完成。
- **i.MX6ULL 屏幕：** 本地传感器读数、CAN 节点心跳/错误计数、日志存储空间和运行状态。
- **电脑上位机：** 完整控制台、视频、曲线、节点状态和日志检索。屏幕触控若硬件支持可作为输入方式；MVP 不依赖触摸操作。

## 4. 通信与控制协议

### 4.1 以太网：电脑 ↔ RK3588

- **视频通道：** RK3588 从 V4L2/GStreamer 取流，使用 RTSP 向电脑提供视频。先以 1080p、30 fps 为目标配置，再按端到端延迟、丢帧和 RK3588 温度调整；不把 4K 推流设为 MVP 门槛。
- **控制/状态通道：** WebSocket 长连接，UTF-8 JSON，一条消息一帧。控制命令包含递增序号和有效期；服务端返回接受/拒绝原因。上位机显示最后收到状态的时间和链路断开状态。
- **安全约束：** WebSocket 断开或控制命令过期时，RK3588 不再续发有效运动命令；F407 自己也必须有命令超时停车，不依赖 Linux 节点正确运行。
- **建议字段：** `type`、`seq`、`timestamp_ms`、`vx_mm_s`、`wz_mrad_s`、`ttl_ms`。速度单位显式写在字段名中，避免浮点单位歧义。

命令示例（字段名和单位是本项目约定，可在开始编码前冻结）：

    {"type":"cmd_vel","seq":1042,"vx_mm_s":120,"wz_mrad_s":0,"ttl_ms":300}

状态示例：

    {"type":"status","seq":1042,"camera_fps":29.8,"can_online":true,"left_rpm":42.1,"right_rpm":41.7,"fault":0}

### 4.2 CAN：RK3588 ↔ F407 ↔ i.MX6ULL

- 第一版采用 **经典 CAN 2.0B、标准 11 位 ID、8 字节以内 payload**，不使用 CAN FD，因 F407 bxCAN 和 i.MX6ULL FlexCAN 的共同能力已足够满足本项目数据量。
- 建议初始波特率 500 kbit/s；如果实测线缆、收发器或总线质量不稳定，降到 250 kbit/s。总线仅在物理两端各保留一个 120 Ω 终端电阻；先检查板上是否已经装有/启用终端电阻，避免重复并联。
- Linux 端用 SocketCAN 的 `can0` 接口，不新造一个自定义 CAN 字符设备。SocketCAN 把 CAN 暴露成网络接口并可通过 socket 收发；Linux 官方文档：[SocketCAN](https://docs.kernel.org/networking/can.html)。
- CANH/CANL 只接 CANH/CANL；板间共地要求按各板电源与隔离设计确认。禁止将 MCU 逻辑 TX/RX 直接接到总线差分线。

建议先实现最小协议，确认控制稳定后再加入传感器帧：

| CAN ID | 方向 | 内容 | 频率建议 | 首版用途 |
|---|---|---|---:|---|
| 0x200 | RK3588 → F407 | 左/右目标轮速、命令序号、租约/超时、使能/急停状态 | 20 Hz | 运动命令 |
| 0x180 | F407 → 其他节点 | 左/右实际轮速、驱动状态、故障位、计数器 | 20 Hz | 电机反馈 |
| 0x080 | 各节点 → 其他节点 | 节点在线、工作模式、故障摘要、递增计数器 | 1–2 Hz | 心跳 |
| 0x300 | i.MX6ULL → 其他节点 | AP3216C 光照/红外/接近读数与状态 | 5–10 Hz | 传感器状态 |
| 0x310 / 0x311 | i.MX6ULL → 其他节点 | ICM20608 加速度 / 角速度数据 | 10–50 Hz | 传感器状态；高频原始数据优先写本地日志 |
| 0x400 起 | STM32F103（可选） | 辅助 I/O 或测试帧 | 按扩展定义 | 预留，不进入 MVP |

所有多字节整数统一采用小端序；有符号速度用二补码；每个帧定义固定缩放比例、有效范围和保留值。CAN 已有链路层 CRC，应用层保留递增计数器用于发现重复/丢帧。最终协议表放在 `common/protocol/spec/`，并由 RK、F407、i.MX6ULL 共用同一份定义文档。

### 4.3 F407 的实时控制行为

- 编码器由定时器编码器模式读取，PWM/方向信号驱动 H 桥。
- 速度环建议从 100 Hz 开始，在 F407 本地完成；CAN 接收、控制计算、显示刷新分层运行，不能用 Linux 调度周期控制电机。
- 目标轮速命令带有效期。F407 若连续 300 ms 未收到有效命令、CAN 进入 bus-off、编码器异常或检测到急停，应把目标轮速清零并将驱动输出置为安全态。300 ms 是本项目的初始设计值，需在实际电机/总线条件下验证后冻结。
- 机械急停应切断电机驱动电源或使能线，不能只依赖软件按钮。

## 5. Linux 驱动学习与实现主线

本项目的原则是：**能自己写的设备专用代码尽量自己写，同时复用 Linux 内核和 SoC 已有的基础设施。**“自研驱动”不是重写 Linux 的 I²C/SPI 控制器、GPIO 控制器、时钟、存储、网卡、显示和相机 ISP 驱动，而是自己实现具体传感器/板级设备的驱动，写自己的设备树配置、用户态采集服务、协议、MCU 固件和上位机。

| 部分 | 本项目做法 | 原因 |
|---|---|---|
| AP3216C、ICM20608 设备专用驱动 | 自己实现、自己调试 | 适合练 I²C、SPI、设备树、IIO、IRQ、缓冲采样和错误恢复 |
| 板级按键、LED、蜂鸣器 | 自己完成板级配置/小驱动练习，接入 input、LED、PWM 等标准子系统 | 既练 platform/设备树/GPIO，又避免创造一套私有通用接口 |
| IMX415 传感器侧驱动 | 自己实现 V4L2 sensor sub-device，作为进阶目标 | 能展示相机驱动经验；依赖已工作的 MIPI 接收、ISP 和媒体框架 |
| SoC 控制器与 Linux 公共框架 | 复用内核/BSP，不从零重写 | 这些是板卡启动和外设工作的底座，重写它们会把项目变成 SoC 移植工程 |
| F407/F103 固件、CAN 应用协议、PC 上位机 | 自己实现 | 这是本项目的控制、通信和应用主体 |

对传感器而言，交付不只是“写寄存器成功”，还要说明设备如何被设备树枚举、驱动如何绑定、数据如何通过标准内核接口交给用户态。字符设备实验单独保留为基础练习，不把所有外设都包装成自定义字符设备。

### 5.1 i.MX6ULL：基础驱动主阵地

1. **基础实验模块（教学用途）：** 自己写模块加载/卸载、参数、错误处理、`miscdevice` 或 cdev、`read/write/poll`、等待队列。完成后保留为独立实验，不把它冒充成传感器的正式接口。
2. **Platform + Device Tree + GPIO：** 自己写小型板级按键/状态实验，练习 `platform_driver`、`probe/remove`、设备树匹配、GPIO descriptor、IRQ/threaded IRQ 和 workqueue。最终按键接 input 子系统、LED 接 LED 子系统、蜂鸣器接 PWM 或已有合适框架。
3. **AP3216C（I²C）：** 不调用正点原子的 AP3216C 驱动实现；以芯片资料、原理图和总线波形为依据，自己写寄存器读写、初始化、状态/数据读取、采样时序和错误处理，再按 IIO 通道暴露环境光、红外和接近数据。若传感器没有引出中断线，首版轮询；不要在没有硬件连线时虚构 IRQ 支持。
4. **ICM20608（SPI）：** 自己写 SPI 事务、ID 检查、复位、量程/采样率配置、加速度计/陀螺仪 IIO 通道和异常恢复。进阶做 IRQ、IIO 缓冲采集、FIFO 和偏置校准。板上引脚复用需要在自己的设备树配置中处理。
5. **CAN 与记录服务：** 复用 SoC CAN 控制器驱动及 SocketCAN，不自己重写 CAN 控制器；自己写 F407 收发协议、i.MX6ULL 用户态 CAN 监听/日志服务和上位机解析。

IIO 为传感器驱动提供统一的内核/用户态接口，包括 sysfs 属性和缓冲数据接口；参考 [Linux IIO 文档](https://docs.kernel.org/driver-api/iio/index.html) 与 [IIO 核心说明](https://docs.kernel.org/7.1/driver-api/iio/core.html)。设备树用于描述硬件连接和资源，而不是把板卡参数硬编码进驱动；参考 [Linux Devicetree 使用模型](https://docs.kernel.org/devicetree/usage-model.html) 与 [绑定规则](https://docs.kernel.org/devicetree/bindings/writing-bindings.html)。

### 5.2 RK3588：摄像头链路与自研传感器驱动

完整理解这条链路：IMX415 传感器寄存器控制 → MIPI CSI-2/PHY → RK3588 摄像头接收/ISP → V4L2 video 节点 → GStreamer/视觉应用。

- 先用可启动 BSP 和已知工作配置作为硬件基线，**不直接编辑厂商源码文件**；之后自己写 IMX415 传感器侧 V4L2 sub-device 驱动和自己的 DTS/设备树覆盖配置。
- 传感器驱动需覆盖供电/时钟/复位 GPIO、I²C 寄存器读写、模式表、MIPI lane/格式、曝光/增益控制和启停流程。具体寄存器模式表和电气时序需从模组资料、芯片资料或合法可用的参考资料确认；若缺少必要编程资料，先完成框架驱动和链路调试，不能靠猜测寄存器值。
- CSI 接收、PHY、ISP、DMA、媒体控制器和 V4L2 核心继续复用内核/BSP已有实现。它们是自研 IMX415 驱动能够工作的底层，不是本阶段要重写的对象。
- 用 `v4l2-ctl --list-devices`、`media-ctl -p` 和 GStreamer 定位链路；不要把 `/dev/video22` 等示例节点号写死在程序里，启动时按媒体拓扑/配置发现设备。
- SH3001 是 RK3588 板载资源。若以后想练另一份 I²C 驱动，可在确认传感器资料、驱动绑定冲突和板级风险后单独安排；MVP 将自研驱动精力集中在 i.MX6ULL 上的 AP3216C/ICM20608。
- V4L2 sub-device 是相机传感器等子设备常用的内核模型；参考 [V4L2 sub-device 文档](https://docs.kernel.org/6.14/driver-api/media/v4l2-subdev.html)。

### 5.3 BSP 与内核版本策略

- 厂商 BSP 只作为已验证的启动基线，原始源码、DTS 和镜像单独归档并记录校验值；自己的驱动、DTS、构建脚本放在项目目录或独立 Git 分支，不直接改供应商原文件。
- 先把自研驱动编译成 out-of-tree 模块，便于快速迭代；正式交付时把模块、自己的 Kconfig/Makefile、DTS 变更和构建说明整理完整。模块必须匹配运行内核的版本、配置、符号版本和工具链。
- 如果原厂驱动已经绑定了同一传感器，先通过自己的设备树副本/覆盖配置禁用原节点或替换 compatible；同一个设备实例不能同时被两份驱动占用。若板卡启动链不支持 DT overlay，就编译并使用自己的 DTB；这仍不需要修改原始厂商文件。
- 每个板卡维护独立内核目录/构建说明，不把 RK3588 和 i.MX6ULL 的 DTS、交叉编译器或补丁混在一个含糊的构建脚本里。记录 `uname -a`、设备树型号、内核配置、SDK 版本、启动介质和根文件系统版本。
- 先在匹配的 BSP 内核上完成，再选一个驱动移植到较新的内核练习 API 变化。i.MX6ULL 官方资料给出的 BSP 内核较老；项目必须标明每个补丁实际验证过的内核版本。
- 设备树遵循现有 binding 和 SoC DTS 的写法。新增硬件描述时，先查已有 binding，再决定是否新增；参考 [DTS 编码规范](https://docs.kernel.org/devicetree/bindings/dts-coding-style.html)。

## 6. 电脑上位机

### 建议技术选型

- **UI：** Python + PySide6，利于快速形成桌面控制台和日志工具；如果目标岗位更偏 C++/Qt，可在 MVP 后将通信/界面逐步迁移到 Qt/C++。
- **通信：** WebSocket 接 RK3588 状态与运动命令；RTSP/GStreamer 或可用的视频组件显示相机流。
- **日志：** 本地 CSV/JSONL 或 SQLite。保存运行时间、命令序号、左右目标/实际轮速、传感器值、告警和链路变化。

### 页面组成

1. **主视图：** RTSP 视频窗口；检测框开关；相机帧率、视频延迟和丢帧提示。
2. **手动控制：** 方向控制/速度滑块；使能状态、急停状态和“松手归零”。速度上限由 RK3588 和 F407 两侧共同约束。
3. **节点状态：** RK3588、i.MX6ULL、F407 心跳；CAN 错误/超时；传感器数据；系统温度/磁盘空间可作为增强项。
4. **曲线：** 目标与实际轮速、IMU 角速度、接近/光照值，支持暂停、导出和时间范围选择。
5. **日志/故障：** 搜索故障码、导出本次记录、查看设备固件/协议版本。

上位机断开后，不允许 F407 保持最后一个非零目标持续运行。所有控制操作应显示当前操作模式，避免键盘焦点变化或窗口失焦导致持续运动。

## 7. 新增采购建议

### MVP 必需

- 两个带正交编码器的直流减速电机，以及与底盘、电池/电源匹配的车轮和支架。
- 双路 H 桥驱动器。按电机供电电压、持续电流和堵转电流选型；不能只看“额定电流”宣传值。
- 带限流能力的电机电源、保险丝、实体急停开关、可靠接线端子/线束。
- CAN 总线线材；若现有板卡没有可切换的终端电阻，准备两个 120 Ω 终端电阻。
- 逻辑板和电机电源分开供电/布线，确认共地或隔离方案，避免电机反电动势和地弹噪声让 Linux 板复位。

### 开发辅助（建议但可选）

- USB-CAN 适配器：独立观察 CAN 帧和错误，比只靠板上日志容易定位接线/波特率问题。
- 万用表；若有条件再准备逻辑分析仪/示波器。
- 额外传感器先不买。现有 RK3588 和 i.MX6ULL 板级资料已经列出 SH3001、AP3216C、ICM20608。等底盘控制和驱动链路稳定后，再按实际需求加编码器计数需求之外的测距/避障模块。

## 8. 分阶段开发计划与交付物

### 阶段 0：硬件盘点与冻结接口

- 拍照记录每块板的正反面型号、硬件版本、屏幕型号、摄像头模组标识、连接器方向。
- 导出每块 Linux 板内核/SDK 信息；记录各板启动介质、IP、串口和屏幕驱动状态。
- 查看探索者板 CAN 收发器型号、终端电阻跳线；查看 RK3588、i.MX6ULL 底板的 CAN 终端配置。
- 选定电机、编码器、驱动器和供电；核对电机堵转电流与驱动器规格。
- 交付：硬件清单、接口表、照片、风险清单、协议草案。

### 阶段 1：各板独立 bring-up

- 每块板都能稳定启动并在本地屏显示对应状态；PC 可通过以太网连接 RK3588。
- RK3588 上 IMX415 可持续取流；检查实际格式、帧率、温升和屏幕显示。
- i.MX6ULL 上先确认 AP3216C、ICM20608 的原厂例程能作为硬件对照，然后停止/禁用对应原驱动，准备自己的模块和设备树配置；明确区分硬件通信成功与自研驱动绑定成功。
- F407 独立读编码器、输出 PWM，并在屏幕展示计数/轮速；此时不接驱动电机或将车轮架空。
- 交付：每块板独立启动说明、版本记录、基线截图/日志。

### 阶段 2：Linux 传感器驱动

- 先完成自研 I²C 驱动，再做自研 SPI 驱动；先用原厂例程验证传感器和硬件连线，再切换到自己的驱动，避免同时有两个驱动争用设备。
- 驱动通过标准 IIO 接口向用户态提供数据；设备树配置、模块构建、日志和错误恢复代码由项目自己维护。
- 用户态采集服务写带时间戳的本地日志，并能从 i.MX6ULL 屏幕观察值是否更新。
- 交付：完整自研驱动源码、自己的 DTS/overlay、模块构建说明、IIO 接口说明、采样记录、误差/校准说明，以及对照原厂参考行为的差异记录。

### 阶段 3：CAN 与电机控制

- 先用 USB-CAN 或虚拟接口验证协议解析，再接板间总线；设置一致的波特率和仅两端终端电阻。
- 先发零速、再低速单轮、最后双轮；每步使用限流电源并将车轮架空。
- 调试 F407 编码器方向、左右轮极性、PID 参数、目标超时、CAN 断线停车和实体急停。
- i.MX6ULL 作为监听/记录节点，验证同一 CAN 帧可被多个节点接收。
- 交付：CAN ID/缩放协议表、F407 控制固件、接线照片、曲线和故障行为记录。

### 阶段 4：RK3588 摄像头与 PC 视频

- 先以原厂 BSP 已知工作配置确认相机模组、排线和 CSI 硬件正常；随后切换到自研 IMX415 sensor sub-device 驱动和自己的设备树配置，再让相机在本地屏与电脑 RTSP 稳定显示。
- 先不叠加 AI；确定端到端延迟和视频编码路径后，再加载轻量检测模型并显示识别框。
- 控制设备节点发现逻辑，启动失败时给出相机链路、媒体拓扑和错误日志。
- 交付：自己编写的 IMX415 sensor driver、DTS/overlay、相机链路说明、V4L2/GStreamer 命令和视频性能记录；CSI/ISP 等底层驱动仍注明所依赖的内核版本与 BSP。

### 阶段 5：电脑上位机与端到端集成

- 接入视频、WebSocket 命令/状态、CAN 电机状态和 i.MX6ULL 传感器状态。
- 完成状态灯、命令有效期、异常弹窗、日志导出、断线归零。
- 三块板各自屏幕显示局部信息；电脑屏幕是总览，不能成为唯一故障指示途径。
- 交付：上位机安装/运行说明、界面截图、日志样例、端到端演示视频。

### 阶段 6：项目收尾与作品集

- 完整 README：系统结构、硬件版本、连接图、启动顺序、编译和烧录方法、常见故障。
- 公开或整理清晰的 Git 提交历史；驱动改动拆成小补丁，不提交厂商 SDK 大文件和闭源二进制。
- 提供关键日志/性能测量，不只放一张运行截图；每项指标附测量条件和方法。
- 交付：代码仓库、开发文档、协议文档、设备树补丁、演示视频、测试/测量报告。

## 9. 验收清单

### 功能验收

- [ ] IMX415 在 RK3588 本地屏和电脑上位机均可预览；切换启动/停止后无设备节点写死问题。
- [ ] F407 能正确报告左右编码器方向和轮速；目标/反馈曲线可导出。
- [ ] RK3588 发送目标轮速后，F407 执行闭环；丢失命令超过冻结的超时时间后停车。
- [ ] i.MX6ULL 能通过 IIO 读取 AP3216C 与 ICM20608 数据；能够记录 CAN 帧和传感器样本。
- [ ] 电脑可操作速度命令并看到节点/传感器/电机状态；网络断开时有清晰提示并且 F407 安全停车。
- [ ] 三块板屏幕分别显示有意义的本地状态。
- [ ] 实体急停能直接使电机驱动进入安全态；复位后不会意外恢复运动。

### 质量与证据

- 给出相机稳定运行时长、分辨率、帧率、CPU/NPU使用、丢帧和端到端延迟；标明是否运行 AI。
- 给出 CAN 线长、波特率、终端电阻位置、错误帧/重发观察方式。
- 给出电机供电、驱动器电流规格、PID 采样周期、速度稳态误差的测量方法和结果。
- 给出 Linux 内核版本、编译环境、设备树补丁、驱动绑定日志和传感器采样范围。
- 给出故障演示：拔网线、停 RK 服务、断开 CAN、触发急停；说明每种故障的预期行为和实测行为。

阈值（例如最大延迟、最大丢帧率、轮速误差）应在选定摄像头模式、电机和驱动器后冻结，不凭空承诺统一数值。记录“测试条件 + 测量方法 + 实测结果”比孤立写一个漂亮数字更能证明能力。

## 11. 风险、待确认项与应对

1. **摄像头接口/SDK差异：** 官方摄像头说明中特别提到默认 CSI 接口和软件版本差异。先按手头镜像逐项验证，再修改设备树；排线安装前断电并核对方向。
2. **屏幕版本差异：** 三块板所配屏的接口、分辨率、触摸控制器可能不同。本文只定义屏幕职责，不预设所有屏共用同一驱动或都有触摸。
3. **CAN 物理层：** SoC/MCU 控制器不等于 CAN 收发器；总线上只能有两个有效端接。用原理图/跳线核对收发器、终端与电平。
4. **电机电流和电气噪声：** 电机堵转电流可能远高于空载电流；未确认电机/驱动参数前不要上车跑。电机电源和逻辑板电源合理分配，使用保险和急停。
5. **Linux 版本跨度：** i.MX6ULL 与 RK3588 的厂商 BSP、驱动 API 和摄像头栈可能不同。版本记录与分板构建是交付的一部分。
6. **功能过多带来的延期：** IIO 驱动、相机链路、实时控制、上位机已经覆盖多类能力。F103、SLAM、更多传感器、云端等都放在 MVP 后，避免四条主线同时开工。
7. **数据偏差：** IMU 原始值不等于姿态角；光照/接近读数受安装位置、遮挡和环境影响；编码器速度受轮径、地面和减速箱间隙影响。界面和报告要注明校准与测量条件。

### 开始实施前需要补齐的实物参数

- RK3588 当前 Linux 镜像/SDK 版本、IMX415 模组版本、使用的 CSI 接口和屏幕型号。
- i.MX6ULL 阿尔法板核心板型号/版本、当前内核版本、屏幕与触摸型号。
- F407 探索者板版本、CAN 收发器和端接跳线配置、屏幕型号。
- 电机额定电压、减速比、编码器线数、堵转电流；拟购双路驱动器型号。
- PC 操作系统、期望移动方式（键盘、手柄或触屏）。

拿到这些信息后，下一版应补充逐脚接线表、设备树节点、启动命令、具体电机参数和控制协议字节表。当前文档已经足够开始做硬件盘点、各板独立启动和 I²C/SPI 驱动练习，但不应据此盲接电机电源或摄像头排线。
